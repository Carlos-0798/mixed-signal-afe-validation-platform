# 从使用任务重新审视 Analog Validation Studio

2026-09-09，所有者授权突破之前的小阶段规划，同时检查内部运行层与交互层。
本轮重点是让已有软件能力更可靠地形成可复用、可交付的工作闭环。

## 产品出发点

AVS 是控制器中立的本地测试与分析工作台。典型任务是拿到一组受控测量或 CSV，
沿用明确的参数与阈值完成分析，判断结果，再把可追溯的结果交给下一位使用者。
它的价值应来自减少重复配置、脚本拼接和手工汇总，保持同一套工程判断与证据规则。
尚未测量人工基线，因此不声称节省了某个百分比的时间或提升了某个倍数的准确率。

## 审查结论与实施取舍

| 发现 | 影响 | 本轮选择 |
| --- | --- | --- |
| 项目预设只能保存/批跑，不能载回 Setup | 重复分析新 CSV 仍需重填参数 | 预设复制到 Configure，保留原件，重新 Review 后运行 |
| 报告服务与 GUI 分离 | 用户为生成带图交付物必须转到 CLI | GUI 保存包含规范 JSON 的完整报告包，并打开本地 HTML |
| 普通采集仅在整段操作前后检查取消 | 已请求取消仍发起后续读取 | 每次读取前检查令牌，仍由现有 worker 执行 cleanup |
| 第二项准备失败会撤销先前已完成产物 | 已完成的有效工作不可追溯 | manifest v4 描述准备失败，保留此前记录与产物，未开始项明确列出 |

这四项直接改善“保存配置→载入修改→审核→运行→形成报告”的日常链路。
没有新建云服务、账号系统、皮肤编辑器或另一套工程算法，也没有把 UI 运行时迁移
作为本轮前提。原来的三主题继续保留。

## 内部结构

- 领域采集仍在 `analog_validation`，可选 checkpoint 不依赖具体 UI 或线程实现。
- 产品层负责 worker、取消、批次、结果与报告发布；manifest 负责记录事实，不把
  准备失败伪装成已运行的 worker、测量或硬件验证。
- GUI 的预设转换进入独立 `dashboard/presets.py`，报告操作面板进入
  `dashboard/report_actions.py`；不继续把这些职责堆进主表单渲染器。
- 报告直接投影已有结果。HTML、SVG 和完整 JSON 必须对应同一份结果；重复目标
  目录拒绝覆盖，发布失败不把未写成的报告标为已保存。
- v1/v2/v3 manifest 按各自原形读取，新写 v4；旧文件不迁移、不重写。

## 验收边界

检查单元行为、真实 Windows Tk 操作链、公共 API golden、CLI JSON/stderr 隔离、
完整测试与 statement coverage、静态检查，以及隔离安装后的实际使用链。
只使用 Simulator、临时 CSV 和新输出目录。测试中的 HOST_TEST 和 SYNTHETIC、
CSV_REPLAY 结果不升级为 BENCH_CONTROLLER 或 BENCH。

逐次取消仍需等待当前 adapter 调用返回。无法确认 cleanup 的 worker timeout 或
最终原子发布失败不伪造完整错误历史。READ/LIVE 原始观察持久化、跨运行曲线叠加、
屏幕阅读器支持仍是独立设计任务；尤其不能把 LIVE 尾部缓存称为全量原始数据。

本轮停止点是核心使用链经过验证后形成新的本地预览，保留未提交状态供所有者评审。
后续优先跟随真实使用反馈，而不是继续为展示增加更多功能。
