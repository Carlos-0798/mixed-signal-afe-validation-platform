## 2. 产品概述

### 2.1 产品名称

软件产品工作名称：**Analog Validation Studio**  
项目总名称：**Configurable Analog Front-End & Validation Platform**

Analog Validation Studio 是一个本地运行、硬件无关、可扩展的测试自动化与数据验证软件。它能够在没有真实硬件时使用模拟器和历史数据完成完整演示，也能在未来通过适配器连接 MSP430、RP2040、STM32、可配置模拟前端或受支持的实验室仪器。

### 2.2 要解决的问题

嵌入式和模拟系统测试经常存在以下问题：

- 每种开发板使用不同协议和工具，分析代码难以复用；
- 人工抄录测量结果容易出错，且缺少原始证据；
- 仿真、合成数据和实物测量容易混在一起；
- 饱和区、坏帧、异常点和仪器限制可能造成虚假结论；
- 更换控制器或测试仪器时，测试流程需要重新编写；
- 初学者难以判断“软件测试通过”和“硬件已经验证”的区别。

本产品通过统一设备适配器、版本化协议、可追溯数据模型、自动分析和报告生成解决这些问题。

### 2.3 产品价值

- **无硬件也可用：** 模拟器和 CSV 回放模式可以完整运行测试流程；
- **控制器无关：** MSP430 是受支持对象，不是软件运行前提；
- **可重复：** 同一输入数据和配置应得到确定性结果；
- **可追溯：** 原始数据、配置、软件版本和数据来源一同保存；
- **可扩展：** 新设备通过适配器接入，不修改分析核心；
- **诚实验证：** 不把合成数据、SPICE 或主机测试描述成实物测量。

### 2.4 目标用户

- 学习嵌入式测试、数据采集和模拟电路验证的学生；
- 需要低成本自动化验证工具的个人开发者；
- 希望统一管理串口遥测、回放数据和测试报告的固件开发者；
- 未来使用本项目 AFE 硬件或 MSP430 Equipment Health Controller 的用户。

## 3. 产品边界

### 3.1 本产品包含

- 本地 Python 软件包；
- 命令行界面和后续图形界面；
- 通用测量与测试数据模型；
- 设备能力协商与适配器接口；
- Simulator、CSV Replay 和 Serial 适配器；
- AFE 协议与 MSP430 兼容 profile；
- DC sweep、迟滞、校准和频率响应分析；
- 测试执行、PASS/FAIL 判断、日志和报告；
- 示例数据、自动化测试、用户文档和开发者文档；
- 第二部分定义的未来低压硬件参考平台。

### 3.2 本产品不包含

- 市电、高压、医疗或安全认证测量；
- 商业计量仪器精度承诺；
- 未经授权的 OSU 实验室使用；
- OSU Lab Bench Monitor Capstone 的代码、数据或团队成果；
- 对所有串口设备或所有实验室仪器的通用支持承诺；
- 在没有示波器证据时宣称完成高频、噪声、相位或稳定性验证；
- 在没有实物数据时宣称硬件误差、可靠性或性能指标已经实现；
- 第一版云账户、远程控制、多用户协作或移动端应用。

### 3.3 与其他项目的关系

**MSP430 Equipment Health Controller：** 独立产品。通过公开、版本化协议和独立适配器兼容，不共享隐藏状态、板级引脚或业务逻辑。

**OSU Lab Bench Monitor Capstone：** 完全独立。不复制仓库、代码、数据、照片、团队叙述或受限成果。

**未来 AFE 硬件：** Analog Validation Studio 的一个官方参考被测对象和验证平台，不是软件运行的必需条件。

# 第一部分：软件产品

## 4. 软件使用场景

### UC-001：无硬件产品演示

用户启动 Simulator，运行 DC sweep 或迟滞测试，查看曲线、分析结果和测试报告。所有记录标记为 `SYNTHETIC`。

### UC-002：历史数据回放

用户导入受支持的 CSV 数据，软件按原始时间或快速模式回放，重新运行分析并生成可追溯报告。

### UC-003：串口实时监视

用户选择设备 profile 和串口，软件解析遥测、校验 CRC、显示状态、记录坏帧并保存原始数据。

### UC-004：自动测试

若设备声明支持刺激输出，软件设置安全范围内的输入，采集响应、执行分析并生成 PASS/FAIL。若设备不支持相应能力，软件明确返回 `UNSUPPORTED`，不能伪造执行。

### UC-005：MSP430 兼容

软件通过 MSP430 profile 读取 Equipment Health Controller 的遥测，映射为通用记录，同时保留原始字段和项目身份。

### UC-006：未来仪器或新控制器接入

开发者根据公开的 `DeviceAdapter` 契约新增适配器，并复用同一套测试、分析和报告功能。

## 5. 软件功能需求

### 5.1 核心数据与来源

| ID | 需求 | 最低验收标准 |
|---|---|---|
| SW-FR-001 | 通用测量模型 | 至少包含时间、通道、数值、单位、状态、来源和质量标志 |
| SW-FR-002 | 测试运行模型 | 保存测试类型、配置、开始/结束时间、软件版本、设备信息和结果 |
| SW-FR-003 | 数据来源标签 | 每条可用于报告的数据明确标记 `SYNTHETIC`、`CSV_REPLAY`、`SPICE` 或 `BENCH_*` |
| SW-FR-004 | 原始数据保留 | 解析、过滤或校准不能覆盖原始输入；原始与派生数据可追溯 |
| SW-FR-005 | 单位明确 | 公共接口使用带单位字段或命名明确的整数单位，不接受含义不明的裸数 |

### 5.2 协议与通信

| ID | 需求 | 最低验收标准 |
|---|---|---|
| SW-FR-010 | CRC | 实现 CRC-16/CCITT-FALSE，并通过标准向量 `123456789 -> 0x29B1` |
| SW-FR-011 | 帧边界 | 支持换行分隔，设置明确的最大帧长度，拒绝超长帧 |
| SW-FR-012 | 严格解析 | 拒绝坏 CRC、缺字段、多余字段、非法 ASCII、无效枚举和越界数值 |
| SW-FR-013 | 序列检查 | 检测丢帧、重复帧、回退和允许的计数器回绕 |
| SW-FR-014 | 协议版本 | 设备和主机能够确认协议版本；不兼容时安全拒绝可选命令 |
| SW-FR-015 | 能力协商 | 连接后获取 ADC、DAC、PWM、数字捕获、安全范围和受支持命令 |
| SW-FR-016 | 串口恢复 | 超时、断线或端口消失时不崩溃，并提供有限重试和可理解错误 |
| SW-FR-017 | 原始帧日志 | 可选择保存接收时间、原始字节、解析状态和拒绝原因 |

### 5.3 设备适配器

| ID | 需求 | 最低验收标准 |
|---|---|---|
| SW-FR-020 | 统一接口 | Simulator、CSV Replay 和 Serial 使用同一上层接口 |
| SW-FR-021 | SimulatorAdapter | 可配置增益、偏置、噪声、饱和、迟滞、丢帧和 CRC 错误 |
| SW-FR-022 | CsvReplayAdapter | 支持合法数据回放、速度控制、暂停和结束状态 |
| SW-FR-023 | SerialProtocolAdapter | 串口细节不泄漏到分析模块 |
| SW-FR-024 | MSP430 profile | 与 AFE profile 分离，映射后仍保留 MSP430 原始字段 |
| SW-FR-025 | 能力降级 | 缺少 DAC、PWM 或边沿捕获时返回明确能力状态，不让整个平台失效 |
| SW-FR-026 | 安全关闭 | 支持的输出设备在测试结束、异常或用户中止时执行 `safe_shutdown` |

参考接口：

```python
class DeviceAdapter:
    def connect(self): ...
    def disconnect(self): ...
    def get_capabilities(self): ...
    def set_stimulus_mv(self, channel, value_mv): ...
    def read_measurement(self, channel): ...
    def read_digital_state(self, channel): ...
    def run_command(self, command): ...
    def safe_shutdown(self): ...
```

具体签名可在 Software Phase 1 调整，但语义和安全责任不能删除。

### 5.4 测试与分析

| ID | 需求 | 最低验收标准 |
|---|---|---|
| SW-FR-030 | DC sweep | 支持输入点序列、重复次数、稳定等待和结果保存 |
| SW-FR-031 | 线性拟合 | 计算增益、偏置、R²、残差和使用点数 |
| SW-FR-032 | 饱和区排除 | 使用可解释规则排除饱和区，并保留所有原始点和排除原因 |
| SW-FR-033 | 迟滞分析 | 分别分析上升和下降扫描，计算上下阈值和迟滞宽度 |
| SW-FR-034 | 校准 | 计算并应用版本化增益/偏置系数，保留校准前后结果 |
| SW-FR-035 | 频率响应 | 根据输入/输出幅度计算比值和 dB，估计 -3 dB 截止频率 |
| SW-FR-036 | 数据质量 | 标记缺失、非有限值、饱和、超范围、时间异常和通信异常 |
| SW-FR-037 | PASS/FAIL | 阈值来自版本化测试配置；不能在缺失必需数据时给出 PASS |
| SW-FR-038 | 可重复性 | 相同版本、配置和输入应生成一致的确定性分析结果 |

### 5.5 用户界面与报告

| ID | 需求 | 最低验收标准 |
|---|---|---|
| SW-FR-040 | CLI | 能列出 profiles、运行模拟测试、回放文件和导出结果 |
| SW-FR-041 | Dashboard | 显示连接、输入/输出、状态、数据来源和当前测试进度 |
| SW-FR-042 | 测试向导 | 用初学者可理解的步骤配置 DC sweep、迟滞和回放测试 |
| SW-FR-043 | CSV 导出 | 导出原始点、派生值、质量标志和元数据 |
| SW-FR-044 | JSON 摘要 | 生成机器可读的测试配置和结果 |
| SW-FR-045 | 人类可读报告 | 包含目标、环境、来源、结果、限制、PASS/FAIL 和未验证项 |
| SW-FR-046 | 错误说明 | 面向用户的错误包含发生了什么、可能原因和安全下一步 |

## 6. 软件非功能需求

| ID | 类别 | 要求 |
|---|---|---|
| SW-NFR-001 | 可安装性 | 从干净的受支持 Python 环境可按文档安装和运行 |
| SW-NFR-002 | 平台 | 第一目标为 Windows 11；核心分析避免 Windows 专用依赖 |

| SW-NFR-005 | 可扩展性 | 新设备 profile 不修改核心分析算法；新分析不要求修改串口驱动 |
| SW-NFR-006 | 可维护性 | 公共 API 有类型、文档和版本；模块责任单一，避免循环依赖 |
| SW-NFR-007 | 性能 | 对低速遥测和常见 CSV 数据保持交互可用；具体上限通过基准测试确定 |
| SW-NFR-008 | 安全输入 | 配置文件和串口数据不能触发任意代码执行；路径、长度和数值均验证 |
| SW-NFR-009 | 隐私 | 默认只在本地保存；未经用户明确要求，不上传测量或日志 |
| SW-NFR-010 | 可追溯性 | 报告记录软件版本、协议版本、配置摘要和输入数据标识 |
| SW-NFR-011 | 可访问性 | 不能只依赖颜色表达 PASS/FAIL 或故障；文本同时说明状态 |
| SW-NFR-012 | 向后兼容 | 公共格式改变时增加版本并提供迁移说明，不静默改变字段含义 |

质量目标：关键协议、CRC、分析和安全状态转换的测试覆盖率目标不低于 90%。覆盖率只是辅助指标，不能代替边界测试和验收测试。

## 7. 软件架构原则

```text
UI / CLI
   |
Application Services: session, test runner, report orchestration
   |
Domain Core: models, analysis, quality rules, acceptance decisions
   |
Ports: DeviceAdapter, DataStore, ReportWriter, Clock
   |
Adapters: Simulator | CSV Replay | Serial | MSP430 | Future Instruments
```

必须遵守：

- 领域分析层不导入串口库、板级 SDK 或 GUI 框架；
- UI 不自己重新实现 CRC、拟合或迟滞算法；
- 适配器负责设备差异，不能改变测量物理含义；
- 配置、输入数据和结果使用版本化 schema；
- 所有自动输出命令经过能力检查和安全范围检查；
- 日志用于诊断，报告用于证据，两者不能互相替代；
- 不为尚未存在的设备实现大量猜测代码，只冻结必要扩展点。

## 8. 软件安全准则

软件本身不能保证外部接线安全，但必须避免主动增加风险。

### 8.1 强制规则

1. 默认连接状态不产生刺激输出；
2. 设备未报告能力和安全范围前，不允许发送自动刺激命令；
3. 超范围请求必须在主机侧拒绝，不能只依赖固件保护；
4. 自动扫描必须有最大值、步数、等待时间和总超时；
5. 用户中止、异常、断线或程序退出时调用 `safe_shutdown`；
6. 不支持安全关闭的设备只能进入明确的只读或人工确认模式；
7. 不把串口名称、设备身份或能力猜测为已确认事实；
8. 回放和模拟模式不能向真实串口发送命令；
9. 报告必须显示数据来源和未验证限制；
10. 不提供市电、高压、医疗或人体连接测试模板。

### 8.2 安全状态

```text
DISCONNECTED
  -> CONNECTED_READ_ONLY
  -> CAPABILITIES_CONFIRMED
  -> ARMED
  -> RUNNING
  -> SAFE_SHUTDOWN
```

禁止从 `DISCONNECTED` 或 `CONNECTED_READ_ONLY` 直接进入 `RUNNING`。第一版可以只实现只读和模拟自动测试，但状态语义必须保留。

## 9. 证据与成果声明规则

| 标签 | 含义 | 可以支持的声明 |
|---|---|---|
| `THEORY` | 公式或手算 | 理论预期 |
| `SYNTHETIC` | 软件生成数据 | 软件流程和算法行为 |
| `CSV_REPLAY` | 历史文件回放 | 解析和分析可重复性；取决于原数据来源 |
| `SPICE_IDEAL` | 理想模型仿真 | 理想拓扑行为 |
| `SPICE_MODEL` | 器件模型仿真 | 模型条件下的预测 |
| `HOST_TEST` | PC 自动测试 | 主机软件行为 |
| `BENCH_DMM` | 实物万用表测量 | 记录条件下的低速电气结果 |
| `BENCH_CONTROLLER` | MCU/ADC 实测 | 指定固件、接线和采样条件下的结果 |
| `BENCH_SCOPE` | 示波器实测 | 指定探头和带宽条件下的波形结果 |

规则：

- 只有 `BENCH_*` 能支持真实硬件性能声明；
- `HOST_TEST` 不能证明 UART 电气、ADC、接线或模拟电路工作；
- `SPICE_*` 不能作为实物测量；
- 缺少环境、配置或原始数据的记录不能升级证据等级；
- 简历、README 和演示材料中的数字必须能回溯到报告和原始数据。

## 10. 软件测试策略

### 10.1 测试层级

- **单元测试：** CRC、字段验证、单位换算、拟合、饱和排除、迟滞、校准；
- **属性/随机测试：** 帧损坏、边界长度、随机数值、编码后再解析；
- **黄金文件测试：** 固定输入对应固定结果，防止格式和算法静默漂移；
- **适配器契约测试：** 所有适配器通过同一行为测试集；
- **集成测试：** Simulator → parser → test runner → report；
- **回放测试：** 合法、截断、缺列、错误单位和非有限值数据；
- **串口替身测试：** 使用内存流或伪终端测试超时、分段和重连；
- **端到端测试：** 从 CLI 启动到生成报告；
- **人工体验检查：** 初学者按 README 能否完成首次运行。

### 10.2 每次阶段验收必须保存

- 执行命令；
- 软件和依赖版本；
- 测试数量及真实结果；
- 示例输入和输出；
- 已知失败与未运行项；
- 数据来源标签；
- 下一阶段入口条件。

## 11. 软件阶段计划

时间是初学者业余开发估算，不是交付承诺。每个阶段必须通过出口条件后才能进入下一阶段。

### Software Phase 0：产品基准与现状审计

**预计：** 1–2 天  
**目标：** 确认当前代码与本规划书的差距，不急于重构。

交付物：

- 本规划书；
- 现有代码、测试和文档清单；
- 需求追踪矩阵初版；
- 架构决策记录目录；
- 当前测试基线和技术债清单。

出口条件：

- 每个现有模块都有“保留、重构、替换或待决定”结论；
- 测试在当前环境真实运行并记录；
- 不把旧报告结果当作本次运行结果；
- Software Phase 1 的文件级计划已确认。

### Software Phase 1：领域模型、配置与协议核心

**预计：** 3–5 天  
**目标：** 建立稳定、无硬件依赖的核心。

交付物：

- 版本化 Measurement、TestRun、Capability 和 QualityFlag 模型；
- CRC 和协议模块；
- 配置 schema、验证和默认值；
- 错误分类和结构化日志；
- 单元、边界和黄金向量测试。

出口条件：

- 核心不导入串口、GUI 或板级 SDK；
- 非法数据有稳定错误类型；
- 公共格式有版本；
- 关键协议测试全部通过。

### Software Phase 2：适配器框架、模拟器与回放

**预计：** 4–6 天  
**目标：** 在没有硬件时完成设备生命周期和数据流。

交付物：

- `DeviceAdapter` 契约；
- SimulatorAdapter；
- CsvReplayAdapter；
- 适配器契约测试；
- 能力协商和只读/可输出状态模型。

出口条件：

- 两个适配器使用同一上层测试流程；
- 模拟器能注入噪声、饱和、迟滞和协议故障；
- 回放不修改原文件；
- 缺少能力时返回 `UNSUPPORTED`。

**阶段成果：软件 MVP。** 此时产品可无硬件演示完整数据流。

### Software Phase 3：测试执行与测量分析

**预计：** 5–8 天  
**目标：** 把独立算法组织成可配置、可追溯的测试流程。

交付物：

- DC sweep runner；
- 拟合、饱和排除和质量标记；
- 迟滞 runner；
- 校准模型；
- 频率响应离线分析；
- PASS/FAIL 规则；
- CSV 和 JSON 结果。

出口条件：

- 每个结论能追溯到原始点和配置；
- 被排除点保留且有原因；
- 不完整数据不能得到 PASS；
- 合成数据的预期故障能够被检测。

### Software Phase 4：串口层与兼容 profiles

**预计：** 4–7 天  
**目标：** 完成可在无硬件条件下测试的真实通信边界。

交付物：

- 串口发现、连接、读取、超时和重连；
- AFE profile；
- MSP430 Equipment Health Controller profile；
- 序列检查和原始帧日志；
- 内存流/串口替身集成测试；
- 硬件实测待办清单。

出口条件：

- 串口模块不包含测量分析；
- profile 不共享项目业务逻辑；
- 分段、粘连、坏帧和断线测试通过；
- 真实 MSP430 未连接时明确标记兼容性未实测。

### Software Phase 5：CLI、Dashboard 与报告

**预计：** 5–8 天  
**目标：** 让非开发者也能运行和理解测试。

交付物：

- 稳定 CLI；
- Dashboard；
- 初学者测试向导；
- 实时或回放曲线；
- 人类可读报告；
- 示例项目和故障示例。

出口条件：

- 从空白终端按文档可启动；
- 数据来源和限制在界面及报告中可见；
- 错误不会只显示 Python traceback；
- 至少一条端到端演示流程通过。

**阶段成果：软件 Beta。**

### Software Phase 6：产品化发布

**预计：** 4–7 天  
**目标：** 形成可独立展示、安装和扩展的 v1.0。

交付物：

- 安装包或明确的 Python 安装流程；
- Windows 发布验证；
- 用户手册、开发者适配器指南和协议文档；
- 示例数据与演示；
- 版本号、变更记录和许可证检查；
- 完整测试和发布报告。

出口条件：

- 干净环境安装测试通过；
- 自动测试和端到端演示通过；
- 所有已知限制有记录；
- README 不包含未获得的硬件成果；
- 新适配器可以仅依赖公开接口实现。

**阶段成果：Analog Validation Studio v1.0 软件产品。**

### 软件总体周期

- 初学者、业余投入：约 4–6 周；
- 集中投入的可展示 MVP：约 2–3 周；
- 实际周期根据现有代码审计、UI 选择和测试问题调整。

# 第二部分：未来硬件参考平台

## 12. 硬件目标

硬件阶段用于提供真实被测对象、参考刺激/采集控制器和实物证据。软件 v1.0 不依赖硬件完成；硬件接入不能要求重写软件核心。

未来成熟形态包含：

```text
AFE Base Unit
  输入保护 -> 缓冲 -> 可配置增益 -> 可配置低通 -> 模拟输出
                     |
                     +-> Schmitt Trigger -> 数字输出

Optional Validation Controller
  DAC/PWM刺激 + ADC采集 + 数字边沿捕获 + USB/UART

Analog Validation Studio
  自动测试 + 分析 + 校准 + 报告
```

## 13. 硬件功能需求

以下全部是未来目标，不是已实现结果。

| ID | 需求 | 预期验收证据 |
|---|---|---|
| HW-FR-001 | 独立 0–3.3 V 低压输入 | 原理图、接线、DMM 输入记录 |
| HW-FR-002 | 输入限流与钳位 | 元件型号、理论边界、受控低压测试 |
| HW-FR-003 | 缓冲级 | 多点 Vin/Vout 数据和稳定性观察 |
| HW-FR-004 | x1/x2/x5/x10 增益 | 理论、SPICE、DMM/ADC 拟合对照 |
| HW-FR-005 | 至少两档低通滤波 | 频响原始数据、-3 dB 估计和仪器条件 |
| HW-FR-006 | 可配置 Schmitt Trigger | 上升/下降阈值重复测量和迟滞统计 |
| HW-FR-007 | 高精度低速 ADC | 原始码、单位换算和参考测量对照 |
| HW-FR-008 | 手动独立模式 | 无 MCU 时仍可配置并观察基本功能 |
| HW-FR-009 | USB 自动验证模式 | 同一软件通过正式适配器完成测试 |
| HW-FR-010 | MSP430 兼容模式 | 独立接线、固件和兼容性报告 |
| HW-FR-011 | 安全默认状态 | 拔掉控制器后无危险输出或未定义驱动冲突 |
| HW-FR-012 | 可维护接口 | 测试点、电压域、方向和 1 脚标识清楚 |

## 14. 硬件安全红线

1. 只进行安全特低电压实验；不接入 110/220 V 市电；
2. V1 外部模拟输入限定为 0–3.3 V，未经验证不得接负电压或更高电压；
3. 外部 5 V 不能直接接入 3.3 V GPIO、ADC、I2C 或模拟节点；
4. 风扇、电机和其他负载不能由 GPIO 或 3.3 V 引脚直接供电；
5. 上电前必须完成电源轨对地阻值、短路、极性、IC 方向和公共地检查；
6. 首次上电使用受控电源或经过确认的低压电源，并记录限流设置；
7. 先测电源轨和 VBIAS，再连接信号源或控制器；
8. 万用表测电压时并联，测电流时串联；电流档表笔绝不能跨接电源和地；
9. USB 仪器、台式示波器和外部电源接地关系必须先确认；
10. 未确认器件完整型号、封装、引脚和数据手册前不得上电；
11. 每颗 IC 就近放置去耦，接线保持短且可检查；
12. 烙铁、焊锡、通风、护目和断电冷却流程到位后才永久焊接；
13. 任何异常发热、气味、电流上升或电压错误立即断电；
14. 没有原始记录、接线照片和仪器条件时，不形成硬件性能结论。

## 15. 硬件采购入口条件

新 AFE 专用硬件暂缓采购。只有以下条件满足后才冻结并下单：

- Software Phase 2 完成，`DeviceAdapter` 和 Capability 模型稳定；
- Software Phase 3 的测试输入、输出和数据字段明确；
- 已决定首个参考验证控制器或明确只做手动第一阶段；
- 采购清单区分“必需、备用、后续、共享工具”；
- 每个关键器件有完整型号、封装、供电、逻辑电平和替代策略；
- 预算含运费、税费、备件和返工余量；
- 用户确认已有工具、MSP430 板、MM420、焊接能力和仪器权限；
- 接线图和首次上电检查表至少有评审版本。

采购时优先 Adafruit 购买模块、线材和通用工具；精密模拟器件和精密阻容只在参数等价时替换，否则使用 DigiKey 等授权渠道。平台偏好不能覆盖电气兼容性。

## 16. 硬件阶段计划

### Hardware Phase 0：设计与采购冻结

**预计：** 2–4 天，不含到货时间。

交付物：原理框图、接口契约、候选原理图、关键计算、BOM、采购检查表、接线和上电计划。

出口条件：安全评审完成；器件型号和替代件确认；没有把 SPICE 当实测。

### Hardware Phase 1：电源、保护与缓冲

**预计：** 2–4 天。

顺序：不开 IC 的电源检查 → 插入 IC → 测 3.3 V/VBIAS → 连接受限 DC 输入 → 验证缓冲。

证据：接线照片、连续性记录、DMM 型号、供电和限流、原始 Vin/Vout 表。

### Hardware Phase 2：可配置增益

**预计：** 2–4 天。

证据：每档多个输入点、拟合结果、饱和起点、异常和重复测量。

### Hardware Phase 3：滤波与迟滞

**预计：** 3–6 天，取决于示波器和信号源。

证据：频响数据、仪器设置、阈值上升/下降扫描和重复性统计。没有合适仪器时允许暂停，不以软件估计替代实测。

### Hardware Phase 4：参考控制器自动化

**预计：** 4–7 天。

交付物：参考控制器固件、硬件 adapter、能力协商、自动 DC sweep、安全关闭和报告。

### Hardware Phase 5：ADC 对照、校准与故障注入

**预计：** 4–7 天。

证据：参考读数、校准前后误差、开路/短路/饱和/通信故障记录和 PASS/FAIL。

### Hardware Phase 6：MSP430 兼容性

**预计：** 3–5 天。

交付物：独立 pin map、固件版本、UART/I2C/GPIO 接线、兼容测试和限制报告。该结果不与 AFE 产品本体的验收混合。

### Hardware Phase 7：永久版本与 PCB

**预计：** 1–3 周加生产运输时间。

入口条件：面包板关键功能已经取得 BENCH 证据；接口和元件值稳定；原理图通过评审。

交付物：KiCad 原理图、ERC、PCB、DRC、Gerber、BOM、装配记录、首次上电报告和面包板对照。

硬件总体周期预计 4–8 周，不含供应和 PCB 运输不确定性。

## 17. 兼容性与扩展策略

### 17.1 稳定边界

- 版本化 DeviceAdapter；
- 版本化协议和数据 schema；
- 明确单位和电压范围；
- AFE、MSP430、RP2040/STM32 和仪器各自独立 profile；
- 测试算法不调用板级 SDK；
- 设备不支持的能力显式返回 `UNSUPPORTED`；
- 新设备通过契约测试后才能标记为受支持。

### 17.2 预留但暂不实现

- SCPI 仪器适配器；
- AD9833 或其他波形源；
- 自定义 USB 控制板；
- 多设备同步；
- 插件发现机制；
- 二阶滤波器和双通道 AFE；
- PDF 报告；
- 远程或云端测试。

“预留”表示架构不阻止未来实现，不表示现在需要编写空壳代码。

## 18. 工程开发流程

每个功能遵循同一闭环：

```text
需求 -> 风险/假设 -> 设计 -> 小步实现 -> 自动测试
     -> 结果与证据 -> 文档 -> 验收 -> 下一阶段
```

### 18.1 开始任务前

- 检查工作区和 Git 状态；
- 不覆盖用户文件，不修改无关内容；
- 明确对应需求 ID；
- 说明本次做什么、为什么、原理、风险和预期输出；
- 区分自动执行内容与需要用户确认的内容。

### 18.2 实现过程中

- 一次只建立一个可验证能力；
- 先写或明确验收例，再实现；
- 保持变更范围小；
- 记录关键决策和失败原因；
- 遇到硬件缺失时使用模拟或替身，但正确标注来源；
- 不通过降低安全或验证标准来“让测试通过”。

### 18.3 完成任务时

- 运行环境允许的测试；
- 报告真实通过、失败和未运行数量；
- 列出修改文件；
- 说明仍未验证的假设；
- 给出下一步入口条件；
- 不把阶段目标写成已经完成。

### 18.4 Definition of Done

一个任务只有同时满足以下条件才算完成：

- 需求和边界明确；
- 实现位于正确模块；
- 正常、边界和错误路径有测试；
- 用户可理解的文档已更新；
- 运行结果真实记录；
- 数据来源和证据等级明确；
- 没有隐藏硬件、账户或环境依赖；
- 已知限制和后续工作列出。

## 19. 需求追踪与变更控制

后续建立需求追踪矩阵，至少包含：

```text
Requirement ID
设计文档
实现文件
测试文件
阶段
状态
证据链接
未验证项
```

需求状态只使用：

- `PROPOSED`：尚未接受；
- `ACCEPTED`：已纳入计划；
- `IMPLEMENTED`：代码存在但未完成验收；
- `VERIFIED_HOST`：主机证据通过；
- `VERIFIED_BENCH`：实物证据通过；
- `DEFERRED`：明确后置；
- `REJECTED`：记录原因后取消。

重大变更流程：

1. 描述变化及原因；
2. 分析安全、兼容性、预算、进度、测试和文档影响；
3. 记录接受、拒绝或后置决定；
4. 更新规划书版本和相关需求；
5. 再开始实现。

## 20. 风险优先级

当前主要风险：

| 风险 | 影响 | 当前策略 |
|---|---|---|
| 软件过早绑定某块板 | 失去独立性 | DeviceAdapter 和 capability 先行 |
| UI 先于核心 | 难测试、重复逻辑 | CLI/领域核心先行，Dashboard 后置 |
| 合成数据被误认为测量 | 成果不可信 | 强制来源标签和报告限制 |
| 协议静默变化 | 破坏兼容性 | schema 和协议版本化、黄金文件测试 |
| 自动输出越界 | 可能损坏硬件 | 能力确认、范围检查、安全状态机 |
| 范围不断扩大 | 无法形成可交付版本 | v1 非目标和阶段出口条件 |
| 采购过早 | 买错器件或返工 | Software Phase 2/3 后冻结硬件需求 |
| 仪器不可用 | 无法完成高频验证 | 软件和低速 DC 独立交付，高频证据后置 |
| 初学者一次学习过多 | 调试困难 | 小步门控、每阶段学习目标和证据 |

详细风险继续记录在 `docs/risk-register.md`。
