## Outcome

Software Phase 2 Step 7 is complete. The formal package now exposes one versioned read-only workflow that accepts the same immutable request for SimulatorAdapter and CsvReplayAdapter.

The workflow owns connection setup and cleanup for one call, confirms capabilities, performs a complete preflight before any read, acquires typed Measurements, and returns structured acquisition status. Missing capabilities return `UNSUPPORTED` without consuming available records. Early replay EOF returns `INCOMPLETE` with partial data and exact remaining counts. Successful acquisition returns `COMPLETED`, which deliberately does not mean engineering PASS.

## Public models and API

- `READ_WORKFLOW_SCHEMA_VERSION = "read-workflow.v1"`;
- `ReadOperation`: `ANALOG` or `DIGITAL`;
- `ChannelReadRequest`: explicit channel, operation, unit, and sample count;
- `ReadWorkflowRequest`: immutable, non-empty, unique-channel request;
- `ReadWorkflowStatus`: `COMPLETED`, `UNSUPPORTED`, or `INCOMPLETE`;
- `ReadWorkflowResult`: capabilities, evidence source, Measurements, and missing requirements;
- `run_read_workflow`: one execution function for every conforming DeviceAdapter.

## Safety and correctness decisions

### Completed acquisition is not PASS

The workflow performs data acquisition only. `COMPLETED` means every requested Measurement exists; it does not evaluate gain, linearity, saturation, hysteresis, accuracy, calibration, safety, or hardware performance. Phase 3 runners remain responsible for versioned criteria and `TestRunResult` conclusions.

### Full preflight before I/O

The workflow checks every requested command, channel, and analog unit first. If one requirement is absent, the result contains no Measurements and stable missing-requirement tokens. This makes unsupported execution atomic and prevents hidden partial consumption.

### Distinct expected and unexpected failures

- absent capability → `UNSUPPORTED` result;
- advertised replay capability but insufficient records → `INCOMPLETE` result;
- communication, CRC, adapter, or programming failure → typed exception;
- already-connected caller-owned adapter → `AdapterStateError` without disconnecting it.

### Guaranteed owned-resource cleanup

The function accepts only a disconnected adapter, then performs connect, capability confirmation, read, and disconnect. `finally` cleanup covers completed, unsupported, incomplete, and exceptional execution. Tests confirm error cleanup and that atomic unsupported preflight does not consume a CSV record.

## Beginner explanation

The adapters are interchangeable plugs; the workflow is the common appliance using the plug. It requests capabilities and data without knowing whether records are generated by a formula or read from a file.

Checking every requirement first is similar to checking that all required tools and parts are present before beginning an experiment. If one is missing, the software reports exactly what is unavailable and leaves the dataset untouched.
